# 数据大屏：数据口径（草案）

> 2026-10-19 起草。界面稿在设计画布"用户端"页第四行：**值守态势墙**（护士站电视，实时）、**运营展示墙**（大厅 / 来访参观 / 领导汇报，近 30 天）。
> 原则同其他页面：平台只取设备原始数据和基础记录，所有统计在客户端做；和交接班报告共用"每分钟状态"和"每晚汇总"（见 [handover-and-rounds.md](handover-and-rounds.md) 第 2 节）。

## 0. 平台现有看板盘点（2026-10-30，藕塘社区实看）

平台路由里带看板性质的页面共 12 个（网页端 V3.7.21）。接口都是平台算好的汇总，按"应用逻辑放客户端"的规则**一个都不直接用**，只当作"要展示什么"的参考。

| 健康画像 | `/care/cockpit/health-portrait` | 选一位长者：人体模型 + 体征、BMI、疾病风险、活动、睡眠 | `/api/member/checked-in-search` 等 |
| 告警中心 | `/care/command-center/alert` | 一 / 二 / 三级告警 × 未处理 / 已处理，6 列卡片流 | `/api/statistics/alert-by-level` |
| 监控中心 | `/care/command-center/monitoring-report` | 家属 / 用户 / 护工人数、今日告警、处理占比、设备类型、设备状态、年龄性别、按月告警曲线 | 复用告警 / 地图驾驶舱接口 + `/api/statistics/member-type-count` |
| 长者全景 | `/care/command-center/panoramic-member` | 按楼栋楼层 / 护理组 / 健康状况分组的长者卡片（在床状态、心率呼吸、AHI） | `/api/room/member-panoramic`、`/api/alert/member-alerts` |
| 房间全景 | `/care/monitoring/room-panoramic` | 按楼层的房间、床位入住格子 | `/api/room/panoramic`、`/api/bed/statistics` |

另有护工派单首页 `/caregiver/home`（订单、收入，业务没在用）、步态 `/gait/trend`（单人），不算机构看板。

**同一机构、同一时刻，各页数字对不上**（藕塘社区 2026-10-30 20:18）：

- 用户数：地图驾驶舱 41、它的性别图只算 3 人、首页性别 2 人、全景"在住"40、监控中心"用户"0
- 床位：首页总床 40 但空床 0、入住 0；房间全景 40 床，页脚又写 39
- 今日告警：首页 52、长者全景 49、告警驾驶舱 52（45+4+2+1）；首页"未处理"16 是全部未处理，告警驾驶舱是今日 6
- 健康驾驶舱"有效监测"2 人、睡眠报告 2 份：只算 AIO 来源（见 site-analysis，按来源查能拿到 31 份）

结论：平台看板的版块可以参考，数字不能用；魔墙的每个数字都要由客户端从长者档案、床位、设备实时数据、告警记录、按来源的睡眠报告自己算，并在屏上写清口径。

## 1. 两块屏的定位

| | 值守态势墙 | 运营展示墙 |
|---|---|---|
| 放在哪 | 护士站、值班室的电视或第二块显示器 | 大厅、接待室，参观和汇报时用 |
| 看的人 | 护理员、护士长 | 家属、来访者、上级、院长 |
| 时间范围 | 现在 + 今晚 | 近 30 天（可切 7 天 / 本月） |
| 刷新 | 实时推送，秒级 | 每 10 分钟重算一次 |
| 隐私 | 默认显示"姓 + 床位"（张 · 302-1），可切成只显示床位 | **一律不出现姓名**，只有汇总数字 |
| 交互 | 没有鼠标，所有信息直接写在屏上；告警出现时整屏提示 | 多页自动轮播，每页 20 秒 |

两块屏都是用户端的"大屏模式"：全屏、按 1920×1080 设计，等比缩放适配其他分辨率；不显示菜单、窗口按钮；开机自启后直接进入（可选）。

## 2. 值守态势墙

### 2.1 顶部

机构名、当前时间（大字）、实时连接状态。连接中断时整条变成橙色"数据中断，屏上内容停在 HH:mm"，避免大家以为一切正常。

### 2.2 左栏：现在

| 指标 | 口径 |
|---|---|
| 在床 | 当前在床的长者数（`careState` 的 tone = bed），下面拆成睡着 / 醒着 |
| 离床 · 在房间 | 不在床但雷达跟踪到人 |
| 不在房间 | 没有心率呼吸也没有跟踪目标，且设备在线 |
| 暂停监测 | 设备 10 分钟以上没有上报 |
| 未处理告警 | 告警中心里 alertStatus = 1 的数量，红底大字；为 0 时显示绿色"无" |
| 今晚 | 20:00 以后：已入睡人数 / 在住人数、夜间离床累计次数（和平时对比） |

所有人数之和 = 在住长者数，界面上写出总数，方便核对。

### 2.3 中间上：楼层态势（主视觉）

- 按楼层一行，每个房间一个方块，方块里每张床一个圆点，颜色是这位长者的当前状态。
- 房间顺序按房间名自然排序；房间、楼层来自长者档案（`/api/member/pages` 的楼栋、楼层、房间、床位），**只显示有人入住的房间**。
- 有未处理告警的房间：整块红色并闪烁，写告警类型和持续时间。
- 离床 ≥ 15 分钟的床位：圆点外加橙色圈，写"离床 18 分"。
- 机构超过 6 层或 120 个房间时，按楼栋分页轮播。

### 2.4 中间下：今晚全院睡眠条（条形码）

- 每位长者一行细条，从 20:00 到现在，每分钟一格，颜色同交接班报告（睡着、在床醒着、离床在房间、不在房间、暂停监测）。
- 按楼层、床位排序，楼层之间留空。几十条细条叠在一起，一眼就能看出谁整晚没睡、谁反复起夜。
- 数据就是交接班的"每分钟状态"，同一份，不另算。

### 2.5 右栏：告警

| 内容 | 口径 |
|---|---|
| 告警流 | 今天的告警，最新在上，分组 1 / 2 / 4（离线、安装姿态不出现）；5 分钟内同一长者同一类型合并 |
| 处理用时 | 今天已处理告警的 `processAt − createdAt` 中位数 |
| 5 分钟内处理 | 今天告警里 5 分钟内处理的比例（阈值同"需关注规则"里的 timelyMinutes） |

## 3. 运营展示墙（近 30 天）

全部是汇总数字，不出现任何个人信息。

| 指标 | 口径 | 数据 |
|---|---|---|
| 连续安全天数 | 距最近一次"跌倒 / 坐地告警超过 timelyMinutes 才处理"的天数。没有这样的记录时，从开始使用客户端那天算 | 告警记录 |
| 守护时长 | 近 30 天所有长者"有监测数据"的分钟数合计，换算成小时 | 每晚汇总里的监测分钟 |
| 及时发现跌倒 / 坐地 | 近 30 天跌倒、坐地类告警中，处理类型为有效的次数 | 告警记录 |
| 平均处理用时 | 近 30 天已处理告警的中位数，按天画趋势线，标出目标线（5 分钟） | 告警记录 |
| 告警时段分布 | 星期 × 小时的热力图（有效告警次数），用来安排人手 | 告警记录 |
| 误报率 | 处理类型为误报的比例，按周 | 告警记录 + 处理类型对应关系 |
| 睡眠质量 | 每晚睡眠评分分成 4 档（≥80 良好、70–79 一般、60–69 偏低、<60 需关注），按周看各档占比 | 每晚按设备来源取的睡眠报告评分 |
| 夜间平均睡眠时长 | 每晚在床睡着的分钟数（22:00–06:00 之外也算，只要在班次 20:00–08:00 内），全院平均，按天 | 每分钟状态 |
| 夜间离床 | 人均每晚夜间离床次数，按天 | 每晚汇总 |
| 监测覆盖 | 近 30 天每晚监测完整（暂停 < 30 分钟）的人次 / 总人次 | 每晚汇总 |

### 3.1 运维端第一版（2026-10-30 实现）

2026-10-30 定：运营墙先在**运维端**做（工作台 › 数据看板 › 数据魔墙），值守态势墙以后放用户端。代码在 `client/apps/ops/src/datawall/`（data.ts 取数、stats.ts 统计、charts.tsx 手写 SVG 图表）和 `pages/DataWallPage.tsx`。

- 舞台按 1920×1080 画，等比缩放；三页（运营概况、告警处置、睡眠健康），每页 20 秒自动轮播；范围可选近 7 天、近 30 天、本月（选择存本机）。"全屏放映"把窗口全屏、只留大屏，Esc 退出，左右键翻页。全屏的处理和监控模式共用 `workspace/fullscreen.ts`。
- 因为运维端没有交接班的"每分钟状态"和"每晚汇总"，第一版改用下面的口径，**守护时长、及时发现跌倒 / 坐地没做**：

| 页 | 指标 | 第一版口径 |
|---|---|---|
| 概况 | 在住长者 | 长者档案里 checkType = 2（已入住）的人数 |
| 概况 | 床位入住率 | 楼栋 → 楼层 → 床位逐层取（`getAllBeds`），有入住长者的床 / 全部床 |
| 概况 | 监测雷达在线 | 雷达列表的 isOnline（同房间、场景页，见在线状态的决定） |
| 概况 | 连续安全天数 | 名字含"跌倒""坐地"的告警，5 分钟内没处理（或至今未处理且已过 5 分钟）的最近一条到今天的天数；31 天内都没有时显示"31+" |
| 概况 | 护理告警、每日护理告警、告警类型 | 告警分组 1 场景、2 事件、4 紧急求助（不含离线、安装姿态），类型超过 6 种的合成"其他" |
| 概况 | 长者年龄 | 档案里的年龄，分 5 档，未填的单独说明。**性别不放**：藕塘社区 40 人里 38 人没填 |
| 概况 | 告警处理结果 | 已处理告警的处理类型名（各机构自定义） |
| 告警 | 处理用时 | `processAt − createdAt` 的中位数，整体和按天；目标线 5 分钟 |
| 告警 | 5 分钟内处理 | 5 分钟内处理的 / 全部护理告警（未处理的算没及时） |
| 告警 | 误报占比 | 处理类型名含"误报"的 / 已处理 |
| 告警 | 待处理 | 近 31 天内还没处理的护理告警 |
| 告警 | 处理用时分布、时段分布 | 5 分钟内 / 5–30 分 / 30 分–2 时 / 2–12 时 / 12 时以上 / 未处理；星期 × 小时热力图（全部护理告警） |
| 睡眠 | 评分、睡眠时长、夜间离床 | 一人一晚一份报告（按看床设备的来源，同用户端 `sourcesOf`），取 `sleepScore`、`sleepSummary.totalSleepMinutes`、`metrics.leaveBedCount` 平均。评分分档 7 天以内按天、更长按周 |
| 睡眠 | 报告覆盖 | 有报告的夜晚里，平均每晚有报告的人数 / 有睡眠设备的人数 |

- 取数：长者档案、实时监护长者列表（取设备类型定睡眠来源）、床位、雷达、近 31 天三个分组的告警（`getAll` 每页 1000 条）。打开时取一次，之后每 10 分钟重取；换范围、翻页不再请求。
- 告警**不存本机**：已结束的天里告警也会被补处理（藕塘社区常隔几天集中处理），缓存会让处理用时过时。数据量不大（藕塘社区 31 天约 1000 条，一页取完）。
- 睡眠报告存本机（`ops.dataWall.nights.<机构>`，一人一晚只存评分、时长、离床次数），已结束的夜晚（报告日期当天 10:00 以后）不再取；后台从最近一晚往前补，同时 4 个请求，页脚显示进度。藕塘社区 40 人 × 30 晚 = 1200 份，浏览器调试版约 1 分钟补完。
- 藕塘社区 2026-10-30 实测数字：在住 40、床位 40/40、雷达在线 27/40、近 30 天护理告警 884 次（离床 840）、处理用时中位数 3 小时 46 分、5 分钟内处理 11%、误报 15%、平均睡眠评分 57、人均夜间离床 5.8 次。

## 4. 数据从哪来、存在哪

- **实时部分**：用户端现有的长者列表 + 实时推送 + 告警中心，不新增请求。
- **今晚条形码**：交接班的每分钟状态（客户端开着时实时累积，缺口补拉）。
- **近 30 天**：
  - 告警：按天取一次存本机，已结束的天不再取。首次打开补拉 30 天（每个分组每页 1000 条，`getAlertsInRange` 已有）。
  - 睡眠评分：每天早上按设备来源取一次昨夜报告（已有 `getOrgSleepReports`），存本机。
  - 每晚汇总：交接班那边每晚算一次存本机（在床、离床、心率呼吸、监测分钟）。这块屏直接读，不重新拉原始数据。
  - 首次使用时只能补到平台还保留的天数（设备原始数据保留多久还没核实，通信日志只有约一个月），之前的数字显示"—"，并在页脚写"统计自 X 月 X 日起"。
- 多台电脑各自算各自的。态势墙所在的电脑要一直开着客户端，"今晚"和"每晚汇总"才完整。
