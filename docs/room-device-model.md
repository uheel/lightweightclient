# 户型、房间、设备的关系（数据一致性分析）

> 2026-10-18。读平台前端代码（`common.90139acb`）+ 李虎机构全部 24 个房间、37 台雷达的只读核对。
> 接口细节见 [site-analysis.md](site-analysis.md)"房间户型与雷达区域下发""场景模板与设备场景"；客户端方案见 [room-radar-simplification.md](room-radar-simplification.md)。

## 一句话

平台上"这台雷达装在哪个房间、区域是什么、告警怎么配"分散在 **7 份互不联动的记录**里，平台只在少数操作时顺手同步其中两三份，**删除、换绑、删区域都不会清理其他记录**。客户端要先认定每个问题以哪份为准，再把其余的当作"需要核对的副本"。

## 对象和关系

```
户型 RoomType ──(建房时整份拷贝一次，之后不联动)──┐
                                                  ▼
楼栋 → 楼层 → 房间 Room ──roomTypeId（只是标签）
               │
               ├─ 房间布置 design（elements[]）
               │    └─ 雷达槽位（type 3）: sn, deviceId, qingLanConfig{ranges[index…]}
               │                    ▲ 只是"写着"一个 sn，不是外键
               ├─ 床位 Bed ── bind-bed-device ──┐
               │                               │
设备 Device(id, sn) ── roomId（bind-room-device）┘
   │  ├─ 属性记录（按 sn 查，实际跟设备记录走）: QL_radar_config / QL_radar_area / QL_radar_design …
   │  ├─ 场景记录（按 deviceId）: device-scene
   │  └─ 长者 Member（device/bind）
   ▼
设备本身：真正生效的区域数组、场景
```

## 7 份记录

| # | 记录 | 键 | 谁会写它 | 不会被谁更新 |
|---|---|---|---|---|
| 1 | 户型设计 | roomTypeId | 户型设计页 | 房间、设备的任何改动 |
| 2 | 房间布置（含雷达槽位的 sn / deviceId / 区域） | roomId | v3 房间设计"保存"；客户端写回 | 设备删除、设备换绑房间、户型修改 |
| 3 | 设备的房间绑定 `device.roomId` | deviceId | 新增设备时选房间；房间设计里"关联设备 / 解绑"；`bind-room-device` | 房间布置的保存（布置里放了槽位不等于绑定） |
| 4 | 床位绑定 | bedId ↔ deviceId | `bind-bed-device` | 设备换房间 |
| 5 | 属性记录 | 接口按 sn，**实际挂在设备记录上** | 下发 / 读取设备属性；**保存房间布置也会悄悄改 `QL_radar_config` 的值** | — |
| 6 | 场景记录 | **deviceId** | 保存场景 | 设备删除后重新添加（新 id 下为空） |
| 7 | 设备本身 | sn | 下发 | 平台任何"只保存"的操作 |

平台的 v3 房间设计按"布置里的槽位 ⊆ 绑定到本房间的设备"来设计：左侧设备列表来自 `GET /api/room/radars?roomId=`（按 #3），点一台设备把占位槽位换成真实设备，保存后才写进 #2；"解绑"调接口改 #3，同时把槽位从画布上去掉（也要保存）。**但只有在这个界面里操作时才会同步**，其他入口（设备页删除、设备页改房间、客户端新增设备）都只动 #3。

## 用 sn 还是 deviceId

设备删除后用同一个 sn 重新添加，会生成新的 deviceId：

| 记录 | 结果（距离test …6711 实测） |
|---|---|
| 房间绑定 #3 | 新增时选了房间就有 |
| 布置槽位 #2 | 槽位的 deviceId 已是新 id（是新增时平台按 sn 改的，还是之后在平台上重新放的，没确认） |
| 属性记录 #5 | **被清空**：只剩重新下发后的 4 条，`QL_radar_design` 也没了（对照：坐起测试有 37 条）。所以接口虽然按 sn 查，记录其实跟着设备记录走 |
| 场景记录 #6 | **为空**，设备上的"跌倒告警"还在 → 平台和客户端都看不到，直到从设备读回 |
| 设备本身 #7 | 区域、场景都还在 |

结论：**能用 sn 关联的地方一律用 sn**（布置槽位、属性、设备本身都认 sn）；deviceId 只在调接口时临时查。客户端里凡是"按 deviceId 取平台记录"的地方（场景、告警），都要考虑"记录为空但设备上有"的情况。

## 区域编号有三个数

| 数 | 在哪 | 规则 |
|---|---|---|
| 画布编号 | 布置 `ranges[].index` | 新区域取最小空闲编号，删掉中间的会留空；列表按 index 排序 |
| 设备编号 | 下发给设备的 `QL_radar_area[i][0]` | **平台 `qinglan-compute` 按列表位置重新编成 0…n-1，不用存的 index**（4*6 实测：画布 0/1/3 → 设备 0/1/2） |
| 场景里的区域号 | 场景条件 / `{{area}}` | 设备只认设备编号 |

没有空号时三者相同，所以平时看不出来。删了中间的区域、还没新增区域补上空号之前，平台画布上显示的编号和设备、场景实际用的不一样，按画布填场景会填错。

客户端原来的问题（2026-10-18 已按下面"客户端的规则"改掉：`zonesOf` 按位置编号、`saveRoomDesign` 保存时重排 index、写回按位置对应、设备区域画布删区域后编号前移、诊断提示空号并可一键重排；用 4*6 真实数据核对，换算结果和平台 compute 一致）：

- `toDeviceArrays` 用存的 index，有空号时和平台下发的不一样 → 诊断会把"设备 0/1/2"判成和布置不一致；如果从客户端下发，设备会收到 0/1/3，和平台下发的结果相反
- `syncLayout.applyDeviceArrays` 写回布置时按"index 相同且类型相同"找原区域，设备编号 2 找不到画布上的 3 → 当成新区域，名称、spaceType、id 都丢了，编号变成 2。用户看到的"客户端自动重新排序"就是这里

## 客户端的规则（建议）

| 问题 | 以谁为准 | 其他记录怎么处理 |
|---|---|---|
| 设备在哪个房间 | **#3 房间绑定**（告警、长者、平台各页面都按它） | 布置槽位和它对不上时在诊断里提示，给"把槽位换成绑定的设备 / 删掉槽位"的修复 |
| 区域长什么样 | **#2 房间布置** | 设备读回（#7）只用来核对；属性记录 #5 不可信（保存布置会改值、re-add 会清空） |
| 区域编号 | **设备编号 = 列表位置** | 本地换算按位置编号（和平台 compute 一致）；保存布置时把 index 重写成 0…n-1，消除空号；写回时按位置 + 类型对应原区域 |
| 设备上的场景 | **#7 设备本身**（读回） | #6 只是缓存；整体覆盖保存前必须先读设备合并（告警配置页已这样做） |
| 槽位指向哪台设备 | **sn** | 槽位里的 deviceId 只做参考，不用它关联 |

### 雷达位置跟着房间，不跟着设备（2026-10-18）

区域描述的是房间（门、床在哪），不是设备。平台房间设计里的"移除设备"（"确定将该设备从当前房间和设计上移除？"）会把雷达元素整个删掉，房间就成了没有雷达的空房间，下次装设备只能回平台房间设计里重新放、重新画。客户端的做法（`rooms/radarSlot.ts`）：

- 设备离开房间（改位置、解绑）时，默认只清掉雷达元素上的 `sn / deviceId / deviceName`，安装方式和区域留下，成为"空位置"；诊断里不算问题
- 给房间装设备（新增设备选了房间、改位置、诊断页"放进布置"）时按顺序找：布置里已有这台 → 布置里的空位置 → **户型里同型号的雷达**（`GET /api/room/v3/current-room-type-design?roomId=`，户型从不随房间变化，正好当模板）→ 空白默认（侧装在上墙中间、2.8 m、床位监护、监测范围裁到墙内、没有区域，之后在设备属性里画）
- 实测：`POST /api/room/v3/design` 接受客户端新建的雷达元素，原样存回；元素 `id` 必须是 32 位十六进制，其他格式会被丢掉。李虎机构 9 个没有雷达位置的房间里 8 个的户型带同型号雷达

诊断页可以加的检查（都用已取回的数据在本地算）：

1. 槽位 sn 不在本机构设备里 → "布置里的雷达已不在本机构"（现在有）
2. 槽位设备没绑本房间 / 绑在别的房间 → 新增"槽位和绑定不一致"
3. 同一 sn 出现在多个房间的布置里 → 新增
4. 绑在本房间但没有槽位 → 现在有
5. 布置里区域编号有空号 → 新增"画布编号和设备编号不一样"，修复 = 重排编号并保存（设备数组不变，不用下发）
6. 场景引用的区域号按设备编号核对（现在按画布编号，空号时会错）

## 还没确认

- 新增设备时选了房间，平台会不会按 sn 把已有槽位的 deviceId 改成新 id（4*6 的槽位已是新 id，来源不明）
- 平台告警 / 事件里的 `rangeName` 是后端按画布编号还是按位置解析的设备上报区域号；有空号时平台事件里的区域名可能是错的
- 槽位 `rangeId` 为空的影响
