# 房间户型与雷达区域：客户端简化方案（草案）

> 2026-10-16。平台规则和接口细节见 [site-analysis.md](site-analysis.md) 的"房间户型与雷达区域下发"一节。
> 这部分属于**运维端**（用户端不放任何配置）。只支持开了 v3（`enableV3`）的机构，老版页面不再考虑（2026-10-17 决定）。

## 客户在平台上要走的路

把一台雷达的"床在哪、门在哪"配好，平台上要经过：

1. 建户型（名称 + 长宽）→ 打开户型设计 → 摆家具、放雷达槽位 → 点开雷达槽位进"区域配置"：选工作模式、顶装/侧装、朝向、高度 → 拖监测边界、拖监护区 → 画门、监护床、普通床 → 保存
2. 建房间时选户型（之后不能改）→ 房间设计里把真实雷达绑到槽位上 → 保存
3. 再找到"下发区域"按钮下发，等设备应答
4. 去场景里配离床、久坐等告警，条件里手填区域编号（模板里的 `{{area}}` 平台不替换）

## 难在哪里

| 问题 | 后果 |
|---|---|
| 同一份配置存在 5 层：户型 → 房间拷贝 → （老版）设备自定义 → 平台属性记录 → 设备 | 客户不知道改哪里才生效，几层之间对不上也看不出来 |
| 户型是"建房时拷贝一次"，之后改户型不会同步到房间；房间也不能换户型 | 改一个户型 = 逐个房间点"从户型更新"再保存再下发；老版甚至要删房间重建 |
| 每个房间都必须有户型 | 只有一间房也得先造一个户型 |
| 暴露了容器、监测边界、监护区、雷达坐标系等内部概念 | 客户要理解"监护床必须在 3 m 的监护区里""普通床不能压监护区"才能画对 |
| 保存和下发是两步，下发结果在另一个面板。实测保存房间设计不下发，却会把平台属性记录改成新值，下发状态还显示"成功" | 保存后以为生效了，设备其实还是旧配置，平台上也看不出来 |
| 前后端校验不一致（重叠只在后端查） | 画完点确定才报英文错误 |
| 场景条件靠区域编号，删区域后编号留空、改区域后编号可能变 | 离床告警悄悄失效，没人知道 |

## 简化后的模型

核心思路：**以"房间里的这台雷达"为唯一编辑对象，客户端里没有"户型"；能在本地算的都在本地算，平台只用来存和下发。**

```
房间
 └─ 雷达（绑定的设备）
     ├─ 安装：顶装/侧装、朝向、高度、工作模式
     └─ 区域：门、监护床、普通床、马桶/淋浴等感应区、干扰区（直接画在房间平面上）
```

### 1. 编辑：在房间平面上直接画

- 一个房间一张图：房间外框（长宽）+ 雷达 + 区域，坐标全用房间坐标（cm），客户只看到"墙、雷达、床、门"
- **容器、边界、监护区自动算，不让客户摆**：
  - 容器尺寸按平台规则由安装方式 + 朝向 + 模式查表，雷达位置也由规则决定
  - 监测边界默认 = 容器和房间外框的交集（自动裁到墙内）
  - 监护区自动放到能包住监护床的位置；放不下时直接提示"监护床离雷达太远，换个装法或挪雷达"
- 区域用预设：拖一个"门"自动贴墙、10 cm 宽；"监护床"默认 90×200；呼吸睡眠模式自动只给一张床
- 校验在本地实时做，取前端和后端规则的并集（含重叠检查），中文提示直接标在出错的区域上
- 实时预览"将下发给设备的数组"：换算规则已在本地复现并和平台逐位核对过，不用每次请求 `qinglan-compute`

### 2. 不要户型，改成"复制布置"

**结论（2026-10-17）：保留户型不会让操作更简便，客户端不做户型。**

- 户型唯一的好处是"很多间一样的房间只配一次"。但平台的户型只在建房时拷贝一次，之后改了也不同步，所以这个好处其实没有兑现。客户还得多理解一个概念，多建一个对象，建房前还要先选好
- 同样的好处用"复制布置"实现，更直接：在一间配好的房间上点"复制到其他房间"，勾选目标房间，客户端把雷达安装和区域拷过去，逐间保存并下发。改了以后再复制一次就行，不用维护模板和房间两份
- 平台要求每个房间都有户型（不带 `roomTypeId` 建房会报错）。客户端在每个机构后台建一个共用的空白户型（例如"通用"），所有新房间都挂在它上面，客户看不到。实测 `roomTypeId` 只是个标签：
  - 保存房间设计不会改它；`PUT /api/room` 能随时改它，而且不动房间设计
  - 房间尺寸跟着保存的设计走
  - 有房间在用的户型删不掉，所以不用担心被误删
- 建房时平台会把房间尺寸设成户型的尺寸，客户端建完要马上按客户填的尺寸保存一次设计（或调 `PUT /api/room/v3/size`）
- 机构里已有的户型不动，平台网页端照旧能看；客户端只把它们当作房间上的一个标签显示

### 3. 保存 = 下发，状态一直看得到

- 一个按钮"保存并下发"：
  1. 写房间设计 `POST /api/room/v3/design`（平台房间详情、轨迹换算都读这一层，必须保持一致）
  2. 写设备属性 `QL_radar_config`、`QL_radar_area`，以及平台用的 `QL_radar_design`、`QL_radar_working_type`。这一步是必须的：实测保存房间设计不会下发
  3. 等 SignalR `DeviceResponse`；设备离线就标"待下发"，上线后提醒或自动补发
- 每台雷达一个同步状态：**已同步 / 待下发 / 下发失败 / 设备与平台不一致**。判断方式：用房间设计在本地算出数组，和设备读回的值比较。**不能用平台属性记录判断**：保存房间设计会改记录的值，但不改下发状态
- 房间列表、设备列表都能按这个状态筛选，"全部补发"一键完成

### 4. 场景按区域"是什么"引用，不按编号

- 场景条件里存的仍是 index（设备只认这个），但客户端界面显示"监护床""卫生间门"
- 套用场景模板时自动填 `{{area}}`：离床、入床类填监护床，马桶久坐填 spaceType = 马桶的感应区
- 保存区域时检查这台设备的场景：引用的编号不存在、或者编号对应的区域类型变了，就提示并给出修正

### 5. 老数据体检

- 一次性扫描机构里所有能配区域的雷达（6 / 13 / 15）：有没有绑进房间设计、房间配置能否通过校验、和设备属性是否一致、场景引用的区域是否存在
- 出一张清单，每项带"一键修复"或"去编辑"

## 分阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 1 只读 | 房间平面 + 区域显示、同步状态、老数据体检 | **已完成**（2026-10-17，运维端"房间"页）。只在"读设备核对"时向设备发读取指令 |
| 2 单房间编辑 | 本地编辑 + 校验 + 换算预览 + 保存并下发 | 已确认保存不会自动下发，下发要单独调用（属性写入，或 `qinglan-install`） |

| 4 场景联动 | 区域名引用、自动填 `{{area}}`、编号失效提醒 | 场景编辑已有基础（`api/scene.ts`） |

## 已确认 / 未确认

- 已确认：户型改动不会同步到房间；房间是户型的拷贝；`roomTypeId` 只是标签，可以随时改；换算规则本地可精确复现；后端校验规则；保存房间设计不下发（但会改平台属性记录）；两条下发路径的报文（见 site-analysis）
- `{{area}}` 就是区域 ID（用户确认）：离床填监护床 ID，区域滞留 / 久坐填对应区域 ID。13 型设备上报的区域号和配置 index 一致（藕塘历史已核对），所以第 4 步"场景按区域引用、自动填 `{{area}}`"对 6 / 13 型都可以做；15 型按同一套属性处理
- 体检要能查出藕塘这种情况：离床告警的区域 ID 填成了门（1），不是监护床（0）。藕塘的 38 台先不改，由用户和客户沟通后处理（2026-10-17）
- 13 型已在设备上实测（ultra跌倒 …C50D）：`{{area}}` 填监护床 ID 0，人只离开床、不经过门，离开后 1～2 秒就告警
- 13 型下发只能用属性写入，`qinglan-install` 对它无效（发的是 6 型报文）。"保存并下发"按设备类型选路径：6 型两种都行，13 / 15 型用属性写入
- 13 型下发后几秒内设备会回 `code 103`（正忙，没接受），改安装方式时第一次下发也一定回 103；隔一会儿重发即可，客户端收到 103 自动在 10 秒后重发一次。左右范围可以正常调（之前"固定 ±3 m"的结论是误读）
- 顶装 ↔ 侧装互换（运维端设备属性 › 安装区域，2026-10-17 在 ultra跌倒 上来回实测）：区域在房间里的位置不变；改顶装时雷达放到房间正中，改侧装时放到最近那面墙的中点、朝房间里看；监测范围换成新装法的最大范围并裁到墙内；高度、模式按装法修正并提示。下发成功后连同新的装法、朝向、雷达位置、监护区一起写回房间布置
- 平台内置的 13 型离床模板把区域 ID 写死成 1。客户端套用模板时要统一换成监护床的 ID
